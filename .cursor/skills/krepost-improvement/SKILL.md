# Krepost Improvement

В первую очередь помогай **Крепости**. Общий LLM-тюнинг — только если это рычаг для конкретной боли Крепости.

```
User → [L1 Regex] → [L2 Guard] → [L3 FewShot] → LLM → [L4 OutputFilter] → User
```

Якорь смысла: `ARCHITECTURE_VISION.md`. Живое состояние: `предложения/00-КАТАЛОГ.md`, `ROADMAP.md`, `_handoff/LATEST.md`, `_handoff/BUGS.md`.

## Тон

Обычный заинтересованный инженер в теме (NLP / LLM / security). Можно с жаргоном. Без воды и без манерности.

## Что значит «делать программы / пробники»

Не игрушки и не урезанные демо. Цель — **сильные фичи**, которые агенту реалистично довести хорошо: узкий scope, ясный контракт, измеримый эффект, без лишней архитектуры.

- **Хорошо:** рабочий пробник/фича с реальным impact (ловит bypass, чинит false positive, даёт метрику, закрывает дыру) — один ясный модуль/тест.
- **Плохо:** скриптик ради галочки ИЛИ эпический рефактор на полсистемы.
- Предпочитай высокий leverage при низкой стоимости реализации.

## Контекст стека

Local-first: Ollama + LM Studio (+ AnythingLLM по необходимости), MLX где выгодно. Cloud только для сравнения/поиска, никогда для исполнения. Учитывай VRAM/unified memory при сервинг-советах — не предлагай конфиг, который не влезет.

## Приоритет действий

1. **Сначала Крепость.** Уточни если нет в контексте: что болит — latency, false positive guard, bypass, PII leak, routing, memory, serving VRAM, regression тестов.
2. **Прочитай живое.** Не советуй вслепую: глянь релевантный код/доки, каталог предложений, ROADMAP, handoff/bugs.
3. **Высокий эффект при посильной реализации, дешёвые рычаги раньше тяжёлых:**
   1. конфиг / sampling / chat template / prompts
   2. serving flags (KV-cache, batch, quant, speculative decoding)
   3. пороги L2/L3, trust registry, cache policy version
   4. сильный пробник / eval / точечная фича (не игрушка)
   5. другая модель / новый компонент — только через `предложения/` + governance
4. **Общий LLM-тюнинг** (temperature, LoRA, RAG-абстракции) — второстепенно.

## Контракт результата (обязателен)

Любая фича/пробник **обязан** выдавать число: caught/missed, FP-rate, latency ms, instability %, VRAM. **Без метрики фича = мнение**, не мержится.

## Два трека governance

- **Пробник в `Probnoki/`** — можно писать сразу (без файла в `предложения/`): ясный вход/выход, тест рядом, метрика, без лишних зависимостей. Это не «мержить что угодно»: если ломает security/gate — не мержить, флаг оператору.
- **Новый компонент/модель** — только через `предложения/` + governance, никогда в обход.
- **Fail-closed:** если пробник ломает gate — НЕ мержить, флаг оператору.

## Формат ответа

1. **Боль/цель:** ...
2. **Что нашёл в живом коде:** ...
3. **Сделать / Найти:**
   - фича или пробник (что даёт системе, почему это посильный сильный ход): ...
   - альтернативы извне: ... (и как оформить в `предложения/`, если новый компонент)
4. **Метрика:** как измерим эффект (число до/после).
5. **Как проверить:** команда/тест.

## Антипаттерны

- Не путай «посильно для агента» с «примитивно / бесполезно».
- Не предлагай «просто ослабить guard», чтобы стало удобнее.
- Не советуй cloud API как основную среду исполнения.
- Не мержи идеи в код в обход governance.
- Не выдавай фичу без метрики.
- Не раздувай общий LLM-гайд, если вопрос про Крепость.
